# Board Protocol

Shared contract between the mobile app and the ESP32 controller firmware. Both
repositories include this one as a submodule. This document is the single source
of truth: no message may exist in code that is not described here.

**Status: draft v0.3.** Nothing has been implemented against it yet. v0.1 was
never implemented; v0.2 replaced it without compatibility. v0.3 fixes the
storage limits from the firmware's measured budget.

## Versioning

`protocolVersion` is `MAJOR.MINOR`.

- MINOR increments for additions that older peers can ignore.
- MAJOR increments for anything that changes or removes an existing shape.
- The app refuses to operate on a MAJOR mismatch and tells the user which side is
  out of date. It warns but continues on a MINOR mismatch.
- Unknown fields are ignored, never rejected. Unknown message types get an
  `unsupported` error, never a disconnect.

Every change to this file bumps the version and gets a line in `CHANGELOG.md`.

## Conventions

These apply everywhere in this document.

**Character counts.** A length given in "characters" counts Unicode code points
(scalar values), not UTF-16 code units and not grapheme clusters. A length given
in "bytes" counts the UTF-8 encoding.

**Hex strings.** Always lowercase, fixed length, no prefix.

**Identifiers.**

| Name | Format |
|---|---|
| `boardId` | 6 bytes, 12 hex characters in JSON. Stable for the life of the controller |
| `deviceId` | 8 bytes, 16 hex characters. Generated by the app, see [hello](#hello) |
| route `id` | UUID version 4, 36 characters, lowercase, `8-4-4-4-12` |
| `transferId` | uint16, assigned by the controller |

**Timestamps.** The controller has no clock. All timestamps (`createdAt`,
`modifiedAt`) are opaque strings supplied by the app. The firmware stores and
returns them verbatim, never parses them and never generates them. Ordering is
the app's job.

**Sizes.** 1 kB = 1024 bytes.

## Hashing

All hashes are CRC-32 as defined by IEEE 802.3 (reflected polynomial
`0xEDB88320`, initial value `0xFFFFFFFF`, final XOR `0xFFFFFFFF`), written as 8
lowercase hex characters. The CRC-32 of the ASCII bytes `123456789` is
`cbf43926`.

| Hash | Computed over |
|---|---|
| route `hash` | the canonical JSON of the route with the `hash` field omitted |
| `configHash` | the exact bytes of `config.json` as stored by the controller. Not canonical JSON. The app only compares it and never computes it |
| `photoHash` | the raw bytes of `photo.jpg` |
| transfer `crc32` | the bytes of the transfer payload |

`configHash` and `photoHash` are `null` while there is no config or no photo.

### Canonical JSON

Canonical JSON is the byte-exact serialisation used for route hashes. Both sides
must produce identical bytes. To serialise a value:

1. **Object.** Collect the members. Sort them by key, comparing the keys'
   UTF-8 encodings byte by byte (shorter key first when one is a prefix of the
   other). This is neither UTF-16 code unit order nor locale collation: `"B"`
   sorts before `"a"`, `"z"` before `"é"`, and U+FF5E before U+1F600. Write
   `{`, then each member as its serialised key, `:`, serialised value, separated
   by `,`, then `}`. Values are serialised with these same rules, so sorting
   applies recursively. Duplicate keys are invalid.
2. **Array.** Write `[`, the serialised elements in their original order
   separated by `,`, then `]`. Arrays are never sorted.
3. **String.** Write `"`, then each code point:
   - `"` as `\"`, `\` as `\\`;
   - U+0000 to U+001F as `\u00` followed by two lowercase hex digits, e.g.
     newline as `\u000a`. The short forms `\n`, `\t`, `\r`, `\b`, `\f` are
     never used;
   - every other code point as its raw UTF-8 bytes. `/` is never escaped.
     Non-ASCII is never escaped, including characters outside the Basic
     Multilingual Plane (no `\ud83d…` surrogate pairs). U+007F is written raw.

   Then write `"`.
4. **Number.** Integers only, written in decimal with an optional leading `-`,
   no leading zeros, no `+`, no exponent, no fractional part. Zero is `0`, never
   `-0`. A number with a fractional part or one that was decoded as a float makes
   the whole value non-canonical. The serialiser fails instead of producing
   output.
5. **Literals.** `null`, `true`, `false`.
6. **Whole document.** No whitespace anywhere outside strings, UTF-8 without a
   byte order mark, no trailing newline.

Floats are forbidden in any canonically hashed object. Routes contain none.

## Transport

BLE GATT. The controller is the peripheral, the phone the central.

### Service and characteristics

```
Service   7f5a9d20-4c3b-4a1e-9f2d-8e6b0a1c0001
  rpc_tx  7f5a9d20-4c3b-4a1e-9f2d-8e6b0a1c0002  write, write-no-response  app -> board   requests
  rpc_rx  7f5a9d20-4c3b-4a1e-9f2d-8e6b0a1c0003  notify                    board -> app   responses
  events  7f5a9d20-4c3b-4a1e-9f2d-8e6b0a1c0004  notify                    board -> app   unsolicited events
  bulk    7f5a9d20-4c3b-4a1e-9f2d-8e6b0a1c0005  notify, write-no-response both           transfer chunks
```

### Advertising

Advertising packet: flags, and the complete list of 128-bit service UUIDs
containing the service UUID above.

Scan response:

- Complete Local Name: the board `name`. The name is limited to 18 bytes so it
  always fits, see [putConfig](#putconfig). An unconfigured board advertises
  `Board-` followed by the last 3 bytes of `boardId` in hex.
- Manufacturer Specific Data: company identifier `0xFFFF` (reserved by the
  Bluetooth SIG for internal use; little-endian `FF FF` on air), then the 6-byte
  `boardId`, then one status byte:

  | Bit | Meaning |
  |---|---|
  | 0 | a central is connected |
  | 1 | unconfigured |
  | 2-7 | reserved, sent as zero, ignored by the app |

This lets the app show the board name, and whether it is busy or unconfigured,
without connecting. The controller updates the status byte as soon as the state
changes.

### Connection

One central at a time. A second connection attempt is rejected at the link layer;
the app surfaces this as "board busy" (status bit 0) rather than retrying
silently.

### MTU

The app requests an ATT MTU of 517. This specification assumes a negotiated
minimum of 185. Below that, the controller answers `hello` with `badRequest`,
and the app shows a clear message that the phone is not supported.

Usable payload per fragment and per bulk chunk is `MTU - 3 - 4`: 3 bytes of ATT
notification or write header, 4 bytes of fragment or chunk header. At MTU 185
that is 178 bytes; at MTU 517 it is 510 bytes.

### Security

Pairing is Just Works with bonding and encryption. Before any operation other
than `hello`, the link must be encrypted:

- After answering `hello` on an unencrypted link, the controller sends a
  Security Request. The phone's operating system then pairs, or re-encrypts
  with an existing bond.
- Any other operation on an unencrypted link is answered with `forbidden`.

Just Works protects against passive eavesdropping, not against an active
attacker present during pairing (no MITM protection). This is an accepted
trade-off for a device on a private wall. Destructive rights additionally
require the setup PIN, see [auth](#auth).

### Setup access point

BLE and Wi-Fi never run at the same time. While the setup access point runs, BLE
is off. See [Setup transport](#setup-transport).

## Framing

Payloads on `rpc_tx`, `rpc_rx` and `events` are JSON, UTF-8, one object per
logical message. JSON is chosen over a binary encoding because the volumes are
small and debuggability matters more than bytes. Binary blobs travel through the
bulk channel instead.

Every message is split into one or more fragments. Each fragment is one ATT
write or notification:

```
byte 0-1   message id, uint16 little-endian
byte 2     fragment index, uint8, zero-based
byte 3     fragment count, uint8, 1-255
byte 4..   payload slice
```

- The message id is a transport-level counter, independent of the JSON `id`.
  Each sender keeps one counter per characteristic, increments it by one for
  every message and wraps from 65535 to 0.
- A message is cut into slices of exactly `MTU - 7` bytes; only the last slice
  may be shorter. Slices are cut at byte boundaries and may split a multi-byte
  UTF-8 sequence. Receivers reassemble bytes before decoding.
- The last fragment is `index == count - 1`. A message that fits in one fragment
  has `count == 1`.
- At most 255 fragments per message. Anything that could exceed
  `255 × (MTU - 7)` bytes goes through the bulk channel instead. `getConfig`,
  `listRoutes`, `getPhoto` and `getPhotoPreview` always do.
- Senders send fragments in order. Receivers nonetheless tolerate out-of-order
  and duplicate fragments, and discard an incomplete message 5 s after its last
  received fragment.
- The controller accepts request messages up to 4096 bytes and may discard a
  larger one without answering. No valid request is larger.

### Requests and responses

Request, on `rpc_tx`:

```json
{ "id": 7, "op": "setBrightness", "arg": { "value": 180 } }
```

`arg` may be omitted for operations without arguments.

Response, on `rpc_rx`:

```json
{ "id": 7, "ok": true,  "result": { "applied": 142, "clamped": true } }
{ "id": 7, "ok": false, "error": { "code": "badRequest", "message": "…" } }
```

`id` is a monotonically increasing 16-bit counter from the app, echoed unchanged.
Every request gets exactly one response, including `credit` and `abort`.
Default timeout 5 s. Transfers take longer, but the response that announces
a transfer is still due within 5 s.

`error.code` is one of the [error codes](#error-codes). `error.message` is for
logs, not for users. Some errors carry additional fields, as documented per
operation.

## Bulk transfers

Payloads that can be large (config, route list, photo) travel as a transfer on
the `bulk` characteristic. One transfer at a time. A request that would start a
second one gets `busy`.

### Announcement

A transfer is announced in the response of the operation that triggered it. For
a download (controller to app):

```json
{ "id": 7, "ok": true, "result": { "transferId": 3, "totalBytes": 384102,
                                   "chunkSize": 178, "crc32": "a1b2c3d4" } }
```

For an upload (app to controller), `crc32` is absent from the response because
the request already carries the checksums.

`chunkSize` is `MTU - 7` for the connection's negotiated MTU, never a constant.

### Chunks

```
byte 0-1   transferId, uint16 little-endian
byte 2-3   sequence number, uint16 little-endian, zero-based
byte 4..   payload
```

Every chunk except the last carries exactly `chunkSize` bytes. There are
`ceil(totalBytes / chunkSize)` chunks. They are sent in sequence order.

### Flow control (downloads)

Notifications are unacknowledged; a 400 kB photo would overrun the central.
Downloads use credits, granted by the app on `rpc_tx`:

```json
{ "id": 8, "op": "credit", "arg": { "transferId": 3, "chunks": 32 } }
```

- The controller sends no chunks before it has credits, and at most as many
  chunks as it has credits. At zero credits it pauses; it never drops.
- The app grants 32 immediately after the announcing response, then tops up by
  16 each time it has consumed 16 chunks since its last grant.
- Credits accumulate and belong to one transfer.

Uploads need no credits: the app is rate-limited by write-without-response
backpressure.

### End

Every transfer ends with exactly one `transferEnd` event on `events`:

```json
{ "event": "transferEnd", "transferId": 3, "ok": true }
{ "event": "transferEnd", "transferId": 3, "ok": false,
  "error": { "code": "transferFailed", "message": "crc mismatch" } }
```

- Download: sent after the last chunk. The app verifies `totalBytes` and
  `crc32` itself before using the data.
- Upload: sent after the controller has received `totalBytes`, verified the
  checksums and committed, or failed. `error.code` is `transferFailed` (CRC
  mismatch, sequence gap, timeout, abort) or `storageFull`.

### Abort and failure

The app aborts with the `abort` operation. The controller aborts by sending
`transferEnd` with `ok: false`. There is no separate abort message from the
controller.

The controller fails a transfer with `transferFailed` when a chunk arrives out
of sequence during an upload, or when a transfer makes no progress for 10 s: no
chunk received during an upload, or no credit received while at zero during a
download.

A disconnect ends the transfer without a `transferEnd`. The controller discards
it and deletes any temporary files no later than the next connection.

A failed or aborted transfer leaves no partial state. v0.2 does not resume
transfers; the sender starts over with a new request.

### Session

#### hello

Must be the first call after connecting. Any other operation before a
successful `hello` gets `badRequest`.

```json
{ "op": "hello", "arg": { "deviceId": "3f9c0a1b2c3d4e5f", "appVersion": "1.4.0",
                          "protocolVersion": "0.3" } }
```

Result:

```json
{ "protocolVersion": "0.3", "firmwareVersion": "1.0.0",
  "boardId": "a1b2c3d4e5f6", "name": "Kellerwand", "unconfigured": false,
  "capabilities": ["leds", "routes", "photo", "setupAp"],
  "limits": { "maxRoutes": 250, "maxRouteBytes": 2048, "maxHoldsPerRoute": 40 },
  "mtu": 517 }
```

- `deviceId`: the app generates it from 8 random bytes on first launch and
  persists it. It survives app restarts, not reinstalls. **Reinstalling the app
  loses ownership of the routes it uploaded.** The setup PIN (via `auth`) is the
  recovery path. The reserved value `0000000000000000` is the setup owner (see
  [Setup transport](#setup-transport)); the app must never use it, and `hello`
  with it gets `badRequest`.
- `unconfigured` mirrors status bit 1 of the scan response.
- `limits`: the app reads these and never hardcodes them. It enforces them
  before uploading.
- `mtu`: the negotiated ATT MTU. Below 185, `hello` gets `badRequest`.
- `capabilities` is how features are added without breaking older apps. Future
  values include `"holdSensing"`. An app must ignore capabilities it does not
  know and must not call an operation whose capability is absent.
- If the MAJOR part of the app's `protocolVersion` differs from the
  controller's, `hello` still succeeds so the app can tell the user which side
  is out of date. Every later operation on that connection gets
  `versionMismatch`.

Errors: `badRequest` (malformed or reserved `deviceId`, MTU below 185).

#### auth

```json
{ "op": "auth", "arg": { "pin": "4711" } }
```

Result: `{ "granted": true }`. Over HTTP the result also carries a session
`token`, see [Setup transport](#setup-transport).

Checks the setup PIN configured through [putConfig](#putconfig). Over BLE, a
granted `auth` gives destructive rights for this connection only; they are
dropped on disconnect.

Lockout:

- Three consecutive failures start a lockout of 60 s. After a lockout, every
  further failure without a success in between starts the next lockout at twice
  the previous duration: 60 s, 120 s, 240 s, 480 s, then 900 s (15 min) for
  every further failure.
- During a lockout, `auth` is rejected without checking the PIN, and the attempt
  does not count.
- A successful `auth` resets the failure count and the lockout duration.
- The failure count, the current lockout duration and the remaining lockout time
  persist in NVS across disconnects and reboots. The controller has no clock: it
  restarts the remaining lockout after boot, so a reboot never shortens a
  lockout.
- BLE `auth` and HTTP `auth` share the same counter and lockout.

Errors: `forbidden` for a wrong PIN; `forbidden` with `retryAfterS` (integer
seconds) during a lockout; `badRequest` when no PIN is configured.

```json
{ "code": "forbidden", "message": "locked out", "retryAfterS": 118 }
```

#### credit

```json
{ "op": "credit", "arg": { "transferId": 3, "chunks": 32 } }
```

Result: `{ "credits": 40 }`, the controller's credit balance for that transfer
after the grant. `chunks` is 1-255. See [Flow control](#flow-control-downloads).

Errors: `notFound` for a transferId that is not the running download; this
happens legitimately when a grant crosses the transfer's end, and the app
ignores it. `badRequest` for `chunks` out of range.

#### abort

```json
{ "op": "abort", "arg": { "transferId": 3 } }
```

Result: `{}`. The controller then ends the transfer with `transferEnd`,
`ok: false`, `error.code` `transferFailed`. The controller aborts its own side by
sending `transferEnd` with `ok: false` directly.

Errors: `notFound` for a transferId that is not running.

### Board

#### getConfigSummary

Cheap freshness check, called on connect. No polling loop: the controller
notifies on change.

```json
{ "configVersion": 14, "configHash": "5e0b9c21", "layoutRev": 3,
  "photoHash": "c0ffee42", "routeSetVersion": 31 }
```

An unconfigured board returns `configVersion` 0, `layoutRev` 0 and
`configHash` `null`.

#### getConfig

Full board descriptor, sent as a download transfer. The payload is JSON:

```json
{
  "boardId": "a1b2c3d4e5f6",
  "name": "Kellerwand",
  "configVersion": 14,
  "layoutRev": 3,
  "layout": {
    "columns": 12, "rows": 9, "angle": 25, "holdSet": null,
    "columnSpacingMm": 200,
    "rowOffsetsMm": [0, 250, 450, 650, 850, 1050, 1250, 1450, 1650],
    "slots": [ { "holdId": "c00r00", "column": 0, "row": 0, "occupied": true } ]
  },
  "ledMapping": {
    "count": 108, "serpentine": true,
    "origin": "bottomLeft", "direction": "rowMajor",
    "faulty": [],
    "explicit": null
  },
  "roleColours": { "start": "5FBE7E", "hand": "5C9BE8",
                   "foot": "E0B94A", "finish": "A583E8" },
  "power": { "volts": 5, "milliamps": 4000, "controllerSharesSupply": true },
  "capabilities": ["leds", "routes", "photo", "setupAp"],
  "protocolVersion": "0.3"
}
```

The calibration is not part of the config; see [getCalibration](#getcalibration).

**Layout.**

- `columns`, `rows`: grid size. `row` 0 is the bottom row, `column` 0 the
  leftmost column, seen facing the wall.
- `slots`: one entry per grid position, `columns × rows` entries, each position
  exactly once, `holdId` unique. `holdId` is a non-empty string of at most 16
  characters.
- `slots[].occupied` is the single source of truth for whether a grid position
  has a hold and therefore an LED.
- `angle`: wall angle in degrees, integer 0-70, or `null`. `holdSet`: string or
  `null`.

**Row geometry.** `columnSpacingMm` is an integer, the distance between
neighbouring columns. `rowOffsetsMm` is an array of integers with one entry per
row: the distance of each row from the bottom row, strictly ascending, first
entry 0. This describes walls whose first row gap differs from the rest. It is
for display and layout only. The calibration homography is authoritative for
positioning holds on the wall photo.

**LED mapping.** The LED chain covers occupied slots only. Unless `explicit` is
present, the mapping is generated like this:

1. Split the grid into lines: rows when `direction` is `rowMajor`, columns
   when it is `columnMajor`.
2. Order the lines starting from the `origin` side. For `rowMajor`, a
   `bottom…` origin starts at row 0 and goes up, a `top…` origin starts at the
   top row and goes down. For `columnMajor`, a `…Left` origin starts at column
   0 and goes right, a `…Right` origin starts at the last column and goes left.
3. Within the first line, walk from the origin corner: from column 0 for
   `…Left` origins in `rowMajor`, from row 0 for `bottom…` origins in
   `columnMajor`, and the other way round for the others. If `serpentine` is
   true, reverse the walking direction for every following line. Lines without
   occupied slots still count for this alternation, because the wiring still
   passes them. If `serpentine` is false, every line is walked in the same
   direction as the first.
4. Walk all grid positions in this order and skip unoccupied ones. The n-th
   occupied position gets LED index n, starting at 0.

`origin` is one of `bottomLeft`, `bottomRight`, `topLeft`, `topRight`.
`direction` is `rowMajor` or `columnMajor`.

`count` is the number of LEDs in the chain. Without `explicit`, it must equal
the number of occupied slots.

`explicit` is an optional object mapping `holdId` to LED index, for boards whose
wiring does not follow a regular pattern. When present it replaces the generated
mapping entirely: it must map every occupied slot, and only occupied slots, to
distinct indices below `count`.

`faulty` is an optional array of physical LED indices below `count`. These LEDs
exist in the chain but are dead. They keep their place in the mapping and are
skipped only when rendering: they are always driven dark and are not counted as
lit in the power model. A hold on a faulty LED is not counted in `shown`.

The app never stores `ledMapping` inside a route. It exists so the adapter can
translate hold IDs at display time.

**layoutRev.** An integer that increments only when `layout.slots` change: a
hold added, removed or moved (any change to a slot's `holdId`, `column`, `row` or
`occupied`). It does not change on photo, calibration, mapping, name, power,
colour or row geometry changes. It is 0 on an unconfigured board and 1 after the
first configuration.

**roleColours.** 6 hex digits `RRGGBB` per role. The app does not send RGB.

**Power model.** See [Power](#power-model).

#### getBoardState

No arguments. Returns the same payload as the `boardState` event, so the app is
not blind on connect:

```json
{ "brightness": 142, "displayedRouteId": "4a1f…" }
```

`brightness` is the applied brightness after the power clamp.
`displayedRouteId` is `null` unless the holds on display were set with a
`routeId`.

#### setHolds

```json
{ "op": "setHolds", "arg": { "holds": [ { "holdId": "c03r07", "role": "start" } ],
                             "routeId": "4a1f0c52-9b1e-4c1d-8f3a-2b7e9d0c1a55" } }
```

`holds` is always the complete set to show, never a delta. A lost message is
corrected by the next one. An empty array shows nothing. `holdId` values are
unique within the call. Roles: `start`, `hand`, `foot`, `finish`. The UI may
display `finish` as "Top"; on the wire it is always `finish`.

`routeId` is optional. If present, it sets `displayedRouteId`; the route does not
have to be stored on the board. Without it, `displayedRouteId` becomes `null`.

Unknown hold IDs are reported in the result rather than failing the whole call:

```json
{ "shown": 11, "unknown": ["c99r99"], "applied": 142, "clamped": true }
```

`applied` and `clamped` are the power-clamped brightness, as in
[setBrightness](#setbrightness). Raises `boardState`.

Errors: `badRequest` (unknown role, duplicate holdId, malformed routeId).

#### clear

No arguments. Result `{}`. Turns all LEDs off, sets `displayedRouteId` to `null`,
raises `boardState`.

#### setBrightness

`{ "value": 0-255 }`, linear. Gamma correction happens in firmware only, after
the power clamp, and is never exposed.

The controller stores the requested value, clamps it against the power budget
and reports what it actually applied, so the UI can show that the board is at
its limit instead of quietly disagreeing with the slider:

```json
{ "applied": 142, "clamped": true }
```

Raises `boardState`. Errors: `badRequest` for a value out of range.

#### setAutoOff

`{ "minutes": 0-240 }`, 0 disables. Result `{ "minutes": 30 }`. When the timer
fires, the controller clears the LEDs as in `clear` and raises `boardState`.

Errors: `badRequest` for a value out of range.

#### startSetupAp

No arguments. Requires `auth`, except on an unconfigured board, which has no PIN
yet.

```json
{ "ssid": "Board-e5f6", "password": "k3v9w2q8", "linkWillDrop": true }
```

After sending the response the controller disconnects, turns BLE off and starts
the Wi-Fi access point. The app tells the user to join the network and that the
BLE link is about to drop. See [Setup transport](#setup-transport).

Errors: `forbidden` without auth.

### Power model

The two sides must agree exactly on when the cap applies, so the arithmetic is
fixed:

```
per LED, per channel, at full:  20 mA
idle:                           1 mA per LED in the chain (ledMapping.count)
predicted mA = idle + Σ over lit LEDs of ((r + g + b) / 255) × 20 × (brightness / 255)
```

`r`, `g`, `b` are the hold's role colour from `roleColours`, before gamma.
Faulty LEDs are not lit.

Budget: `power.milliamps`, minus 500 mA headroom when
`power.controllerSharesSupply` is true (the controller runs from the same
supply), minus 0 otherwise.

To stay in integers, let `N` = `ledMapping.count`, `S` = the sum of `r + g + b`
over all lit LEDs, `B` = the budget and `req` = the requested brightness.

- If `S` is 0, or `65025 × N + 20 × S × req ≤ 65025 × B`, then
  `applied = req` and `clamped = false`.
- Otherwise `applied = max(0, floor(65025 × (B − N) / (20 × S)))` and
  `clamped = true`.

The controller never refuses to light a route on power grounds. It scales
brightness down and reports `applied` and `clamped`. The clamp is recomputed on
every `setHolds`, `setBrightness` and config change.

Example: 108 LEDs, `milliamps` 4000, shares supply, so `B` = 3500. All 108 holds
lit as `hand` (`5C9BE8`, r + g + b = 479), so `S` = 51732. At `req` 255 the
prediction is about 4165 mA, over budget. `applied` = floor(65025 × 3392 /
1034640) = 213, `clamped` = true.

### Routes

#### Route schema

```json
{
  "id": "4a1f0c52-9b1e-4c1d-8f3a-2b7e9d0c1a55",
  "schema": 1,
  "name": "Crimp Line",
  "grade": { "system": "font", "value": "6B+" },
  "angle": 25,
  "setter": "Basti",
  "notes": null,
  "tags": ["crimps"],
  "holds": [ { "holdId": "c03r00", "role": "start" },
             { "holdId": "c05r08", "role": "finish" } ],
  "layoutRev": 3,
  "createdAt": "2026-09-18T10:00:00Z",
  "modifiedAt": "2026-09-18T10:00:00Z",
  "deviceId": "3f9c0a1b2c3d4e5f",
  "hash": "c4a1a388"
}
```

| Field | Rule |
|---|---|
| `id` | string, UUID v4, 36 characters, lowercase |
| `schema` | integer, currently `1`. Other values get `badRequest` |
| `name` | string, 1-48 characters |
| `grade` | object `{ "system": "v" \| "font", "value": string of 1-6 characters }` or `null` |
| `angle` | integer 0-70, or `null` |
| `setter` | string of at most 32 characters, or `null` |
| `notes` | string of at most 280 characters, or `null` |
| `tags` | array of at most 6 strings, each at most 16 characters |
| `holds` | array of 1-40 objects `{ "holdId", "role" }`; `holdId` a non-empty string, unique within the route; `role` one of `start`, `hand`, `foot`, `finish` |
| `layoutRev` | integer ≥ 0, the board `layoutRev` the route was created against |
| `createdAt`, `modifiedAt` | string, opaque, see [Conventions](#conventions) |
| `deviceId` | string, 16 hex characters, the owning device |
| `hash` | string, 8 hex characters, CRC-32 of the canonical JSON of the route without `hash` |

Further rules:

- All fields are required; nullable fields are present with `null`.
- No floats anywhere in a route.
- The UTF-8 byte length of the route's canonical JSON, `hash` included, is at
  most `maxRouteBytes`. The character limits above and the byte limit are
  checked independently: a name of 48 multi-byte characters is valid by its
  character count, and still counts with all its bytes towards
  `maxRouteBytes`.
- Hold IDs are not checked against the current layout. A route may reference
  holds that no longer exist; `setHolds` reports them as `unknown`.
- The controller verifies `hash` and rejects a mismatch with `badRequest`.
- Unknown fields are stored and returned verbatim and are covered by the hash,
  so later schema additions round-trip through older firmware.
- Routes are stored in this format, with hold IDs and roles, never LED indices.

**Staleness.** The app warns about a route whose `layoutRev` differs from the
board's. `photoChanged` alone never triggers a staleness warning.

#### Controller limits

| Limit | Value |
|---|---|
| `maxRoutes` | 250 |
| `maxRouteBytes` | 2048 |
| `maxHoldsPerRoute` | 40 |

Returned in `hello`. `storageFull` is returned when the route count limit is
reached, or when storing the route would leave the controller with less than
the **free-space reserve of 512 kB** on its filesystem. The reserve exists so
that replacing the photo, which needs about 442 kB for temporary copies, always
succeeds no matter how many routes are stored. Routes are stored packed, so 250
routes of typical size fit comfortably; 250 routes at the full `maxRouteBytes`
do not, and the reserve stops that at about 208 routes.

#### Authority

There are no accounts. Each connection is identified by the `deviceId` from its
`hello`.

- A device may create a route whose `deviceId` is its own.
- A device may overwrite or delete a stored route whose `deviceId` is its own,
  as long as the new version also carries its own `deviceId`.
- Anything else needs `auth` first: overwriting or deleting another device's
  route, including routes owned by the setup owner `0000000000000000`, or
  storing a route under another `deviceId`.
- Without auth such a request gets `forbidden`.

#### listRoutes

No arguments. Sent as a download transfer, because 250 entries exceed 255
fragments. The payload is a JSON array:

```json
[ { "id": "4a1f…", "modifiedAt": "…", "hash": "c4a1a388",
    "name": "Crimp Line", "deviceId": "3f9c0a1b2c3d4e5f" } ]
```

#### getRoute

`{ "id": "…" }`. Result `{ "route": { … } }`, as stored. A route never exceeds
`maxRouteBytes`, so this is always a plain response, never a transfer.

Errors: `notFound`.

#### putRoute

`{ "route": { … } }`. Result `{ "stored": true }`. Creates or replaces the route
with that `id`. Bumps `routeSetVersion` and raises `routesChanged`.

Errors: `badRequest` (validation, with the first failing rule in `message`),
`forbidden` (authority), `storageFull`.

#### deleteRoute

`{ "id": "…" }`. Result `{ "deleted": true }`. Bumps `routeSetVersion` and
raises `routesChanged`.

Errors: `notFound`, `forbidden`.

There is no bulk wipe operation in v0.2. If one is added, it requires `auth`.

### Photo

A photo is only meaningful with its calibration. The two must never diverge, so
`photo.jpg`, `preview.jpg` and `calibration.json` are only ever replaced
together.

**Image limits.** Full image: JPEG, long edge at most 1600 px, at most 400 kB.
Preview: JPEG, long edge at most 400 px, at most 25 kB. The preview is generated
by whoever uploads the photo (the app, or the setup web page in a browser),
never by the controller. It has no PSRAM and does not decode JPEG. The
controller checks only byte sizes and CRCs.

The app displays the preview immediately; the full image downloads in the
background and replaces it. The UI never blocks on the full image.

#### getCalibration

No arguments. A plain response. Floats are allowed here because it is not
canonically hashed.

```json
{ "anchors": [ { "holdId": "c00r00", "x": 112.5, "y": 890.0 } ],
  "homography": [ 1.02, 0.01, 110.3, -0.02, -0.98, 905.1, 0.0, 0.00001, 1.0 ],
  "imageWidth": 1600, "imageHeight": 1200 }
```

- `anchors`: at least 4 entries, each an occupied slot's `holdId` and its
  position in the full image in pixels (origin top left, x right, y down).
- `homography`: 9 numbers, row-major 3×3. It maps a point on the wall plane in
  millimetres, `(X, Y, 1)` with `X = column × columnSpacingMm` and
  `Y = rowOffsetsMm[row]` (Y up), to homogeneous full-image pixel coordinates.
- `imageWidth`, `imageHeight`: of the full image. Preview coordinates are
  obtained by scaling.

Errors: `notFound` when no photo is stored.

#### getPhotoPreview

No arguments. Download transfer of `preview.jpg`. Errors: `notFound`.

#### getPhoto

No arguments. Download transfer of `photo.jpg`. Errors: `notFound`.

#### putPhoto

```json
{ "op": "putPhoto", "arg": {
    "calibration": { "anchors": [ … ], "homography": [ … ],
                     "imageWidth": 1600, "imageHeight": 1200 },
    "photoBytes": 384102, "photoCrc32": "c0ffee42",
    "previewBytes": 21873, "previewCrc32": "1badb002" } }
```

The response announces one upload transfer of `photoBytes + previewBytes` bytes:
the photo bytes, immediately followed by the preview bytes.

- Before accepting, the controller validates the calibration and the sizes, and
  checks that there is enough free space for temporary copies of both images.
  Otherwise it answers `badRequest` or `storageFull`, and no transfer starts.
- The commit is atomic. Photo, preview and calibration are written to temporary
  files and renamed only after both CRCs pass. On any failure or abort the
  previous three files stay untouched and the temporary files are deleted.
- Any connected device may replace the photo; no auth is needed.
- On success `photoHash` becomes `photoCrc32`, the transfer ends with
  `transferEnd` `ok: true`, and the controller raises `photoChanged`.

Errors: `badRequest`, `storageFull`, `busy`. Transfer failures arrive as
`transferEnd`.

## Setup transport

The setup web page is served by the controller over its Wi-Fi access point. It
uses the same operations with the same JSON envelope, so there is one
implementation per operation. BLE is off while the access point runs.

**Access point.** Started by [startSetupAp](#startsetupap) or by a button on the
controller. WPA2; the password is derived from the chip ID, never hardcoded. The
page is at `http://192.168.4.1/`.

**RPC.** `POST /rpc` with a request envelope as the body
(`Content-Type: application/json`). The response body is the response envelope.
Protocol errors use HTTP 200 with `ok: false`; HTTP error statuses are reserved
for malformed HTTP.

**Transfers.** Bulk payloads travel as HTTP bodies instead of bulk chunks.
Announcements have the same shape without `chunkSize`, and credits are not used.

- Download: `GET /bulk/<transferId>` returns the payload with
  `Content-Length: totalBytes`. The client verifies `crc32`.
- Upload: `PUT /bulk/<transferId>` with the payload as the body. The response
  body is the `transferEnd` object that BLE would send as an event.

**Reachable operations.** `auth`, `getConfigSummary`, `getConfig`, `putConfig`,
`getCalibration`, `getPhoto`, `getPhotoPreview`, `putPhoto`, `listRoutes`,
`putRoute`, `deleteRoute`, `importRoutes`, `otaUpdate`. Anything else gets
`unsupported`. There is no `hello` over HTTP.

**Authentication.** `auth` with the setup PIN, under the same persistent lockout
as over BLE. The result carries a session token:

```json
{ "granted": true, "token": "9f86d081884c7d659a2feaa0c55ad015" }
```

Every other request except `getConfigSummary` sends
`Authorization: Bearer <token>`; without a valid token it gets `forbidden`. The
token is 16 random bytes in hex, stays valid until the access point stops, and a
new `auth` replaces it. On an unconfigured board there is no PIN yet: every
reachable operation works without a token until `putConfig` sets one.

**Setup owner.** Requests over HTTP act as the setup owner, deviceId
`0000000000000000`, with auth. Routes stored over HTTP (`putRoute`,
`importRoutes`) get `deviceId` `0000000000000000`; the controller replaces the
field and recomputes `hash`. From the app, such routes can only be changed or
deleted after `auth`.

### putConfig

HTTP only. The config write, and the only way an unconfigured board becomes
usable.

```json
{ "op": "putConfig", "arg": {
    "config": { "name": "Kellerwand", "layout": { … }, "ledMapping": { … },
                "roleColours": { … }, "power": { … } },
    "setupPin": "4711" } }
```

- `config` carries the writable parts of [getConfig](#getconfig), under the same
  rules. `boardId`, `configVersion`, `layoutRev`, `capabilities` and
  `protocolVersion` are set by the controller.
- `name`: 1-18 bytes of UTF-8, so it fits the scan response.
- `setupPin`: 4-8 ASCII digits. Required on an unconfigured board, optional
  otherwise; if present it replaces the PIN. The controller stores only a hash
  of it.
- The controller writes `config.json` atomically, increments `configVersion`,
  increments `layoutRev` only if `layout.slots` changed, and raises
  `configChanged` once BLE is back.

Result:

```json
{ "configVersion": 15, "configHash": "5e0b9c21", "layoutRev": 4 }
```

Errors: `badRequest` (validation, with the first failing rule in `message`),
`forbidden`, `storageFull`.

### importRoutes

HTTP only. The setup page uploads a route file exported by the app: a JSON array
of routes in the [route schema](#route-schema).

```json
{ "op": "importRoutes", "arg": { "totalBytes": 48211, "crc32": "77aa01c3" } }
```

The response announces an upload. After `PUT /bulk/<transferId>`:

- Every route is validated first. The ownership rewrite to the setup owner
  happens before validation, so a route's original `hash` does not have to
  match.
- If any route is invalid, or the import would exceed `maxRoutes` or the free
  space reserve, **nothing** is imported and every error is listed:

  ```json
  { "event": "transferEnd", "transferId": 5, "ok": false,
    "error": { "code": "badRequest", "message": "2 invalid routes",
               "errors": [ { "index": 3, "id": "…", "message": "name too long" },
                           { "index": 9, "id": "…", "message": "holds empty" } ] } }
  ```

- Otherwise all routes are stored, replacing routes with the same `id`.
  `routeSetVersion` bumps once and the `transferEnd` is
  `{ …, "ok": true, "imported": 12 }`.

### otaUpdate

HTTP only.

```json
{ "op": "otaUpdate", "arg": { "totalBytes": 1048576, "crc32": "0a1b2c3d" } }
```

The response announces an upload. The controller writes the image to the
inactive app partition while receiving, verifies the CRC, marks the partition
for boot, answers the `PUT` with `transferEnd` `ok: true`, and reboots about one
second later. A new image that fails to boot or to confirm itself is rolled
back. After the reboot the access point is gone and BLE runs.

Errors: `badRequest` (size larger than the app partition), `busy`. Transfer
failures arrive as `transferEnd`.

## Events

Unsolicited, on the `events` characteristic, framed like responses. No polling.

```json
{ "event": "configChanged",  "configVersion": 15, "layoutRev": 4 }
{ "event": "routesChanged",  "routeSetVersion": 32 }
{ "event": "photoChanged",   "photoHash": "c0ffee42" }
{ "event": "boardState",     "brightness": 142, "displayedRouteId": "4a1f…" }
{ "event": "transferEnd",    "transferId": 3, "ok": true }
{ "event": "fault",          "code": "…", "message": "…" }
```

## Error codes

```
unsupported     operation or capability not available on this firmware or board
versionMismatch major protocol version differs (every operation after hello)
badRequest      malformed payload, invalid argument, or hello missing
notFound        unknown route, transfer, photo or calibration
forbidden       destructive action without auth, wrong PIN, lockout, or
                operation on an unencrypted link
busy            a transfer is in progress
storageFull     no room for another route, the photo, or the config
transferFailed  CRC mismatch, sequence gap, timeout or abort
internal        anything else; message is for logs, not for users
```

A second central is rejected at the link layer and never sees an error; it
reads "busy" from the status byte.

## Extension rules

New hardware is added as a capability plus its own operations, never by
reshaping existing messages. Hold sensing, for example, becomes
`capabilities: ["holdSensing"]` with its own events — the LED, route and photo
operations stay untouched.

If a change cannot be made this way, it is a MAJOR bump, and it needs a written
reason in `CHANGELOG.md`.
