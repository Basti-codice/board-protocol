# Fixtures

Example data that app and controller both test against (PROTOCOL.md §12).
`PROTOCOL.md` is the contract; these files show it byte for byte.

Everything in this folder except this README is generated by
`tools/generate_fixtures.py`. Never edit a generated file by hand: change the
script, run it, and commit script and output together.

```
python tools/generate_fixtures.py
```

The script deletes and rewrites everything in `fixtures/` except this README,
then reads the files back and checks them. It prints one line per check and
exits with 1 if a check fails.

**The committed files are authoritative.** The script writes byte-identical
files on every run. The one exception is the two PNG files in `resources/`:
their image data is compressed with zlib, and another zlib version may produce
different (equally valid) bytes. If that happens on your machine, keep the
committed files. Tests read the files and never regenerate them.

## 1. Conventions for all files

**Paths.** Paths in this README and inside fixture files are relative to
`fixtures/` and use `/`.

**JSON files**

* UTF-8 without BOM, 2-space indentation, LF line endings, one final newline.
* Strings are raw UTF-8; `\u` escapes appear only for control characters
  (§3). Route 58 is named `"Grüne Leiste"` and its setter is `"Jörg"`, so byte
  limits (§3) are exercised: an umlaut counts 2 bytes.
* Key order follows PROTOCOL.md. A receiver must not depend on key order or
  whitespace. On the wire (`frames/`) the same JSON is sent compact: no
  whitespace, same key order.
* Numbers are integers. `null` appears only in the layout resources.

**A message fixture contains only the payload.** The 5-byte header (§4) is not
part of it. `type` and `kind` follow from the file name, and the `id` plays no
role in these files. Header and `id` are covered by `frames/`.

* JSON message: the file is the JSON payload.
* Binary message (`.bin`): the file is the raw payload, without header.
* Requests with an empty payload (`describe`, `getSettings`, `getStatus`) have
  no file. Their message is the header alone, with `length = 0`.

**File names of message fixtures**

```
0xTT-<message>[.<variant>].<kind>.<ext>           top level
errors/0xTT-<message>.<code>-<codeName>.error.json
```

* `TT`: the `type` in lowercase hex (§9).
* `<message>`: the message name from §9.
* `<kind>`: `request`, `response`, `event` or `error`.
* `<ext>`: `json` or `bin`.

Example: `0x10-setLeds.staleSettings.error.json` is the payload of an error
(`kind = 3`) with `type = 0x10`.

**Binary files** always have an annotated hex dump next to them:
`<name>.hexdump.txt`. In `frames/` there is one `message.hexdump.txt` per
message and no dump per packet. The PNG files have no dump.

### Hex dump format

```
# comment lines start with '#'
0000: 0c 00                                            # settingsRevision = 12 (uint16 LE)
0002: 00                                               # reserved = 0
0005: 7b 22 70 72 6f 74 6f 63 6f 6c 56 65 72 73 69     # payload, JSON (UTF-8)  |{"protocolVersi|
```

* A data line has four parts:
  * the offset in hex, at least 4 digits,
  * `:`,
  * up to 16 bytes as two-digit lowercase hex, separated by single spaces,
  * optionally a comment after `#`.
* To parse: drop everything from the first `#`, skip empty lines, split at the
  first `:`. The offsets run from 0 without gaps. All bytes in order are
  exactly the `.bin` file.
* A line never crosses a field boundary or a packet boundary. The comment on the
  first line of a field names the field and its value. JSON text and chunk data
  also show an ASCII view `|…|` (non-printable bytes as `.`).
* In `frames/`, a line `# ---- packet mtu23/001.bin` marks the byte at which
  that packet starts.

The `.bin` file is authoritative; the dump is for reading and review.

## 2. Reference wall and board

All fixtures use the reference wall of §12.

| | |
|---|---|
| wall face | 1800 × 2200 mm (`face: {w: 1800, h: 2200}`) |
| grid | 12 columns × 12 rows, centred on the face |
| hold centre, column `c` | `x = 75 + 150·c` mm |
| hold centre, row `r` | `y = 300` mm for row 0, `y = 400 + 150·(r − 1)` mm for `r ≥ 1` (100 mm between rows 0 and 1) |
| `positions[i]` | `[round(x · 10000 / 1800), round(y · 10000 / 2200)]`, rounded to the nearest integer (no value falls exactly on .5) |
| holds | every position has a hold |
| LEDs | rows 0–8, 108 LEDs; rows 9–11 have none (`ledMap` `null`) |
| chain | snake from the top left: row `r` even → `r·12 + c`, row `r` odd → `r·12 + 11 − c` |

Board values used throughout:

| Field | Value |
|---|---|
| `protocolVersion` | 1 |
| `boardId` | `a4cf128e` |
| `name` | `Basement` |
| `storageId` | `5be0a913` |
| `settingsRevision` | 12 |
| `holdsRevision` | 5 |
| `ledCount` | 108 |
| `roles` | start `#00c853`, hand `#2962ff`, foot `#ffd600`, finish `#aa00ff` |
| `power` | 4000 mA budget, 20 mA per channel |
| `angleAdjustable` | `false`, so no route in the fixtures has `angle` |
| `maxConnections` | 3 |
| `maxMessage` | 4096 |
| `maxChunk` | 512 |
| `maxRouteHolds` | 64 |
| `maxBatch` | 10 |

### resources/

| File | Content |
|---|---|
| `layout.json` | the wall **before any hold change**: holdsRevision 0, `holdChanges` all 0 |
| `layout.holdChanges.json` | the **current** wall, holdsRevision 5. Same `positions` and `ledMap` as `layout.json`. `holdChanges`: c8 r3 = 5, c5 r6 = 5, c6 r2 = 4, c2 r10 = 3, all others 0. **This is the layout resource of the board:** `size` and `sha256` in `getSettings`, and in `xferBegin` for `layout`. |
| `layout.holdRemoved.json` | like `layout.holdChanges.json`, but the hold at c6 r2 (chain index 30) is removed: `positions` and `ledMap` are `null` there, LED 30 is unused. `holdChanges` there stays 4. Used only by `derived/route-warnings/`. |
| `photoPreview.png` | 32 × 39 px |
| `photo.png` | 160 × 196 px |

The layout files are JSON as in §5.1. For readability, each of the three grid
arrays has one grid row per line. `size` and `sha256` always refer to the exact
bytes of the file, final newline included; those are the bytes the board
transfers.

The PNGs are 8-bit RGB images in one colour, `#808080`, with `mime` =
`image/png`. `getSettings.photo` and the `xferBegin` response carry their real
size and SHA-256.

## 3. Message fixtures (top level)

The files of the §12 tree. Where PROTOCOL.md has an example, the fixture uses
its values. The exceptions and additions:

| File | Note |
|---|---|
| `0x03-getSettings.response.json` | `layout` = size and sha256 of `resources/layout.holdChanges.json`; `photo` = real values of the two PNGs (`image/png`, 32 × 39 and 160 × 196) |
| `0x10-setLeds.request.bin` | route 42 on the current layout: settingsRevision 12, routeId 42. Identical to `derived/route-to-frame/holdWithoutLed.bin` |
| `0x20-syncIndex.response.json` | since 87: route 42 (rev 88) and a tombstone for route 17 (rev 89), `routesRevision` 92, `more: true`; revisions 90–92 would follow on the next page |
| `0x20-syncIndex.reset.response.json` | `reset: true`, complete index without tombstones: routes 3, 42, 58, `more: false` |
| `0x21-getRoutes.response.json` | route 42 as in §10.1 without `angle`; 17 and 103 missing |
| `0x22-saveRoute.invalidPosition.error.json` | `201` for a hold at c12 r3, outside the grid |
| `0x23-updateRoute.request.json` | the complete route as it should be stored. `createdAt` is sent with its stored value; the board keeps its own anyway (§9.13) |
| `0x30-xferBegin.*.json` | resource `photo`, `chunkSize` 234 (= MTU 247 − 13, §6.2), `transferId` 3, real size and sha256 of `resources/photo.png` |
| `0x31-xferChunk.event.bin` | the first chunk of that transfer: transferId 3, offset 0, the first 234 bytes of `photo.png` |

No route in any fixture has `angle`, because the reference wall has
`angleAdjustable: false`. This includes `syncIndex` and `getRoutes`.

**Linked values.** These values agree across all fixtures:

* the reference wall and the board values above;
* the resources (sizes, hashes);
* `transferId` 3 in all transfer messages;
* the wall state. The `setLeds` request shows route 42, and its response has
  `wallSeq` 3108. `getStatus` has `wall = {source "app", routeId 42, wallSeq
  3108}` and brightness 160, and `wallChanged` carries the same values.

All other numbers (`routesRevision`, `rev`, route IDs, tokens) are examples per
message, mostly taken from PROTOCOL.md. They do not form one timeline. For
example, the `saveRoute` response (rev 88) and route 42 (rev 88) both come from
PROTOCOL.md, and `statusChanged` reports settingsRevision 13 after a change.

## 6. derived/route-to-frame/

Route + layout + roles → the `setLeds` payload the app must send (§9.7).

**Input `<name>.json`**

```json
{
  "layout": "resources/layout.holdChanges.json",
  "settings": "0x03-getSettings.response.json",
  "settingsRevision": 12,
  "routeId": 58,
  "route": { "routeId": 58, "rev": 91, "name": "Grüne Leiste", "…": "…" }
}
```

| Field | Meaning |
|---|---|
| `layout` | path of the layout resource; supplies `cols`, `rows`, `positions` and `ledMap` |
| `settings` | path of the `getSettings` fixture; supplies `ledCount` and `roles` |
| `settingsRevision` | goes into bytes 0–1 of the payload |
| `routeId` | goes into bytes 3–6 of the payload. `0` = not a board route; the route object then has no `routeId` and no `rev`. Otherwise `route.routeId` has the same value. |
| `route` | a route object as in §10.1 |

**Expected output**

* `<name>.bin` is the complete `setLeds` payload, without the 5-byte message
  header. The layout of the 331 bytes:

  | Bytes | Content |
  |---|---|
  | 0–1 | `settingsRevision`, uint16 LE |
  | 2 | reserved, 0 |
  | 3–6 | `routeId`, uint32 LE |
  | 7… | `ledCount` × R, G, B in chain order |

* `<name>.hexdump.txt` annotates every LED with its grid position and colour.

**Rule.** Start with `ledCount × 00 00 00`. For every hold of the route:

1. Skip it if it lies outside the grid or `positions[i]` is `null`.
2. Look up `led = ledMap[r·cols + c]`, and skip the hold if that is `null`.
3. Set the three bytes of `led` to `roles[role]`.

Brightness is not applied in the frame.

| Case | Route | Checks |
|---|---|---|
| `ordinary` | 58: two start, three hand, one finish | the normal case |
| `allRoles` | 61: start, hand, foot, finish, each on a position with LED | all four role colours |
| `holdWithoutLed` | 42 (§10.1) | foot c4 r10 has no LED and stays dark |
| `chainEnds` | 73: finish c0 r0, start c11 r8 | LED 0 and LED 107 (the last three bytes) |
| `onlyHoldsWithoutLeds` | 80: holds in rows 9–11 only | all 324 colour bytes are 0 |
| `routeIdZero` | a private route that is not on the board | routeId 0 → `00 00 00 00` |
| `routeIdNonZero` | routeId 305419896 = `0x12345678` | byte order: `78 56 34 12` |

## 7. derived/route-warnings/

Route + layout → the holds the app flags as possibly outdated or missing (§5.4).

**File `<name>.json`**

```json
{
  "layout": "resources/layout.holdChanges.json",
  "route": { "routeId": 42, "holdsRevision": 4, "holds": [ "…" ], "…": "…" },
  "expected": {
    "outdated": [ { "c": 5, "r": 6 } ],
    "missing": []
  }
}
```

`layout` and `route` are the input; `expected` is the result. The board's
`holdsRevision` is not part of the input and is not needed (§5.4).

**Rule.** For every hold of the route, at `i = r·cols + c`:

1. **missing** if `c` is outside `0 … cols − 1`, `r` is outside
   `0 … rows − 1`, or `positions[i]` is `null`;
2. otherwise **outdated** if `holdChanges[i] > route.holdsRevision`.

* A missing hold appears **only** in `missing`, even if its `holdChanges`
  value would make it outdated.
* Both lists are sorted in reading order: by `r`, then by `c`. Do not sort by
  `r·cols + c`, because that index is ambiguous outside the grid.
* Positions are written as `{ "c": …, "r": … }`, and an empty result is `[]`.

| Case | Layout | Route | outdated | missing |
|---|---|---|---|---|
| `noWarning` | holdChanges | holdsRevision 2, holds only on positions with holdChanges 0 | – | – |
| `outdated` | holdChanges | route 42, holdsRevision 4; c5 r6 changed at 5 | c5 r6 | – |
| `notOutdatedEqualRevision` | holdChanges | holdsRevision 3, hold on c2 r10 with holdChanges 3 (3 > 3 is false) | – | – |
| `missingHoldRemoved` | holdRemoved | hold on c6 r2, whose hold was removed | – | c6 r2 |
| `missingOutsideGrid` | holdChanges | hold on c12 r4 (the grid has columns 0–11) | – | c12 r4 |
| `outdatedAndMissing` | holdRemoved | holdsRevision 3, holds deliberately not in reading order | c8 r3, c5 r6 | c6 r2, c12 r5 |

In `outdatedAndMissing`, c6 r2 has holdChanges 4 > 3 and still appears only in
`missing`.

Routes with missing holds would be rejected by `saveRoute` today (§9.12). They
stand for routes that were stored before the wall changed. All other route
fields keep the limits of §10.1.

## 8. frames/

Complete messages as they go over BLE, split into packets (§4.3).

```
frames/<name>/
  message.bin            complete message: 5-byte header + payload
  message.hexdump.txt    annotated, with the packet boundaries of both MTUs
  mtu23/000.bin …        packets for MTU 23, in sending order
  mtu247/000.bin …       packets for MTU 247, in sending order
```

* A packet carries `MTU − 3` bytes: 20 at MTU 23, 244 at MTU 247.
* The message is cut from byte 0 into pieces of that size. Every packet is full
  except the last, which is shorter and not padded.
* Packet files are numbered from `000` with three digits. Concatenating them in
  order gives `message.bin`.
* JSON payloads are compact: the fixture's JSON without whitespace, same key
  order.

| Folder | type | id | flags | Payload = | Packets MTU 23 / 247 |
|---|---|---|---|---|---|
| `0x01-hello.request` | `0x01` | 1 | `0x00` JSON, request | `0x01-hello.request.json` | 3 / 1 |
| `0x10-setLeds.request` | `0x10` | 5 | `0x01` binary, request | `0x10-setLeds.request.bin` | 17 / 2 |
| `0x03-getSettings.response` | `0x03` | 3 | `0x02` JSON, response | `0x03-getSettings.response.json` | 35 / 3 |
| `0x31-xferChunk.event` | `0x31` | 0 | `0x05` binary, event | `0x31-xferChunk.event.bin` | 13 / 1 |

* The IDs follow a session: hello 1, describe 2, getSettings 3, getStatus 4,
  setLeds 5. An event has id 0.
* The `getSettings` response needs several packets even at MTU 247.
* The `xferChunk` message is exactly 244 bytes: 5 + 5 + 234, one full packet
  at MTU 247.

## 9. grades.json

Appendix A as data.

```json
{
  "font": ["4", "4+", "5", "…", "9A"],
  "v": [
    { "v": "V0", "shownFor": ["4", "4+"], "stored": "4" },
    "…"
  ]
}
```

| Field | Meaning |
|---|---|
| `font` | every Font grade, in order from easiest to hardest; the only values a route's `grade` may have |
| `v` | V0 … V17 in order |
| `shownFor` | the Font grades displayed as this V grade; every Font grade is in exactly one `shownFor` |
| `stored` | the Font grade stored when a user enters this V grade; always one of `shownFor` |

## 10. What the script checks

The script checks, among other things:

* **File format:**
  * every file matches what was generated;
  * every file of the §12 tree exists;
  * the JSON form described above (UTF-8, LF, 2-space indentation, final
    newline);
  * every hex dump parses back to its `.bin`.
* **Reference wall:**
  * layout geometry against the §5.1 example;
  * the snake chain;
  * the relation between the three layouts.
* **Resources:**
  * the PNGs are valid;
  * sizes and hashes in `getSettings` and `xferBegin` are the real ones.
* **setLeds:**
  * every `setLeds` payload is exactly 7 + 3 × 108 = 331 bytes;
  * every expected frame decodes back to the holds of its route in their role
    colours, and matches expectations written by hand.
* **Routes:**
  * warnings match expectations written by hand;
  * every route keeps the limits of §10.1, including no control characters in
    text fields.
* **Messages:**
  * `syncIndex` ordering and flags;
  * `getRoutes` against `maxBatch`;
  * `wallSeq` and the linked wall state;
  * error file names and code coverage.
* **frames/:** headers and packet splitting.
* **Sizes:** every request payload against `maxMessage`. The same holds for a
  `saveRoute` and an `updateRoute` with `maxRouteHolds` holds and every field at
  its limit. Their text is either only quotes and line feeds, which take 2 bytes
  each on the wire (the largest possible message), or a mix of multi-byte
  characters, quotes, backslashes and line feeds.
* **grades.json:** against Appendix A.
